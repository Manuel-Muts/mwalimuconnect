# MwalimuConnect

A mobile-first Next.js starter for connecting Kenyan schools and educators around teaching vacancies, including positions where teachers are employed by Boards of Management (BOM), and education internships.

## Run locally

1. Install Node.js 20.9 or newer.
2. Copy `.env.example` to `.env.local`.
3. Run `npm install`, then `npm run dev`.
4. Open [http://localhost:3000](http://localhost:3000).

Configure `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to enable authentication, live vacancy loading and applications. These are the browser-safe URL and publishable key; `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are also accepted by server-side code. The public page contains no sample vacancies; the workspace requires an authenticated Supabase session and an authorized profile role. There is no sample-data or role-preview mode. Apply all SQL migrations in `supabase/migrations` to the Supabase project.

## Supabase setup

The migrations create teacher profiles, institutions, vacancies, applications and subscriptions, along with row-level security policies. Teacher signup requires a county; free teacher accounts can read published vacancies only in that county. Teachers can buy nationwide access, which is enforced by database row-level security. Super admins select a school's county, subcounty and institution type (`Primary + JSS` or `Senior School`). School heads choose a vacancy teaching level: ECDE / Early Years, Lower Primary, Upper Primary, JSS, or Senior School. Primary + JSS institutions can post the first four levels; Senior School institutions can post Senior School vacancies only. Database migration `202610270004` updates existing institution types and vacancy levels and enforces this relationship. Migration `202610280001` adds Monthly, Termly and Yearly subscription records for teachers and institutions. It makes institution vacancies read-only when access expires and allows paid teachers to discover vacancies nationwide. The subcounty selector uses the MIT-licensed `kenya-locations` package. Existing institutions need their subcounty filled in before they can publish vacancies after migration `202610270003`. Existing teacher accounts are prompted to choose a county once. A super admin registers the institution and sends an invitation; the head follows the link once to set a password, then signs in with that email and password on future visits. If the link is expired or already used, a head who set a password can sign in normally; otherwise, the administrator must send a new invitation. Set `NEXT_PUBLIC_SITE_URL` to the canonical deployed app origin and add its `/?setup=password`, `/?email_confirmed=1` and `/?reset_password=1` URLs to Supabase Auth's allowed redirect URLs (and add the matching localhost URLs for local development). Enable email confirmations in Supabase Auth so teacher signups must confirm their address.

When running with `npm run dev`, institution subscription checks are bypassed for the institution dashboard and vacancy publishing, and teacher applications can be submitted without subscription checks so school data flows can be tested before billing is ready. Development-only write endpoints still verify the signed-in account, role, and submitted data; production continues to enforce database subscription policies. Do not expose a development server or its credentials to untrusted users.

Password sign-in for teachers, institution heads and administrators is followed by a six-digit email code. The sign-in form also supports passkey sign-in; the Profile dialog lets signed-in users add, rename, and remove their passkeys. Accounts without a passkey receive an in-workspace setup invitation at most once every 30 days on a supported secure browser. The user must click its setup button to start the device's passkey-registration prompt. Passkeys use Supabase Auth directly and do not request the custom email sign-in code. The frontend uses `@supabase/supabase-js` 2.105.0 or later. In the Supabase Dashboard, enable passkeys and set the relying-party ID and allowed origins to match the canonical production domain and local development origin. Use HTTPS in production; localhost is supported for development. Keep the relying-party ID stable because changing it can make previously registered passkeys unusable. Passkey support also depends on the user's browser and device.

The sign-in form supports password recovery: Supabase Auth sends a reset link, and the app lets the user choose a new password after the verified recovery callback. Customize the reset email in the Supabase Dashboard under Authentication → Email Templates → Reset Password, and ensure the recovery redirect URL is allowed as described above. Apply migration `202610280003_email_otp_sign_in.sql`, then configure `BREVO_SMTP_HOST`, `BREVO_SMTP_PORT`, `BREVO_SMTP_USER`, `BREVO_SMTP_KEY`, `AUTH_OTP_FROM_EMAIL` and `AUTH_OTP_SECRET` as server-only environment variables. Use the Brevo SMTP host and credentials from your Brevo account (the default host and port are `smtp-relay.brevo.com` and `587`). SMTP credentials configured inside Supabase are not automatically available to this app, so also add them to `.env.local` and your deployment environment. `AUTH_OTP_FROM_EMAIL` must be a sender address verified with Brevo. Generate `AUTH_OTP_SECRET` from at least 32 random bytes; keep it private and consistent across deployments so pending sign-ins can be decrypted. Brevo SMTP sends the sign-in codes, and their HTML/text email design is generated by `sendOtpEmail` in `src/lib/auth-email-otp.ts`; it does not depend on a preconfigured gateway template. Supabase Auth separately sends teacher email-confirmation links using its configured SMTP/email provider. Customize that message in the Supabase Dashboard under Authentication → Email Templates. Do not prefix these server secrets with `NEXT_PUBLIC_` or expose them in browser code.

Teachers create and maintain a details-only CV from the `My CV` dashboard section; no file upload is required. Their account name and email prefill the form; a saved CV, including a candidate statement explaining why they fit the position, is required to apply. Migration `202610280004_teacher_cv_applications.sql` creates the CV table and limits institution access to CVs belonging to teachers who applied to one of that institution's vacancies. Migration `202610280006_teacher_cv_candidate_statement.sql` adds the candidate statement field and enforces it for new applications. Apply migration `202610290001_break_application_cv_policy_recursion.sql` to avoid recursive application/CV row-level-security checks when institutions view applicants. Teachers can update their CV metadata at any time; institutions see the latest saved version for their applications. The institution Applications section shows applicants to their active vacancies, with an action to view each CV. After applying, teachers are told that the school will contact them if they are shortlisted. Institution heads set an application closing date when posting a vacancy. The dashboard displays an Open/Closed status using the Africa/Nairobi date; closed vacancies cannot accept applications. Migration `202610280005_vacancy_application_deadline.sql` adds the deadline and database-side application enforcement.

To bootstrap the first super administrator, apply the SQL migrations, then run `npm run seed:superadmin` from an interactive terminal. The script asks for the administrator's name and email and prompts for a password without displaying it. It creates or promotes that Supabase Auth user and sets the matching `profiles.role` to `admin`. The script requires `SUPABASE_URL` and `SUPABASE_SECRET_KEY` in `.env.local`. Keep the secret key server-side only; never expose it in browser code or commit it. `SUPABASE_JWKS_URL` is not currently needed because authentication is verified through Supabase Auth. Afterward, the in-app admin flow can register institutions and send head-of-institution invitations.

The super-admin Institutions and Vacancies tables stay cached in the dashboard while navigating between sections. Use each table's Refresh action to load current data; institution registrations, edits and deletions invalidate the institution cache automatically.

## IntaSend setup

Set `INTASEND_SECRET_KEY`, `INTASEND_PUBLIC_KEY`, `INTASEND_WEBHOOK_CHALLENGE` and plan prices in the server environment: `SUBSCRIPTION_WEEKLY_AMOUNT_KES` (teacher-only), `SUBSCRIPTION_MONTHLY_AMOUNT_KES`, `SUBSCRIPTION_TERMLY_AMOUNT_KES`, and `SUBSCRIPTION_YEARLY_AMOUNT_KES`. Until a plan price is set, that plan appears as unavailable. Weekly duration defaults to 7 days; monthly, termly, and yearly durations default to 30, 90, and 365 days respectively. These can be overridden with their matching `SUBSCRIPTION_*_DAYS` variables. The subscription form calls `/api/billing/checkout`, which sends an M-Pesa STK push request using the secret key on the server. In IntaSend, create a webhook for the `collection_event` topic pointing to `https://your-domain.example/api/billing/webhook`; set its challenge to the same value as `INTASEND_WEBHOOK_CHALLENGE`. The endpoint checks the challenge, provider, currency, amount, invoice reference and payment state before activating access. Install all SQL migrations before enabling checkout. A successful renewal extends access from the current expiry date; institution vacancy writes are blocked by database row-level security after expiry.

## Current MVP boundary

Teacher signup, county-scoped vacancy access and applications use Supabase. Institution registration/invitations and vacancy authoring are available only to authorized administrator and subscribed school accounts. Institution invitations include a first-time password setup flow. Monthly, Termly and Yearly plans are offered to teachers for nationwide vacancy access and to institution heads for school workspace access. Subscriptions are activated through IntaSend payment webhooks.
